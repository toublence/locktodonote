이벤트 자료 사용자 제공 65개 이벤트와 총 사용자 69명

**현재 기능으로 초기 유료 구매를 유도할 여지는 있지만, 안정적인 구독 갱신과 큰 매출을 기대하기에는 유료 기능의 반복 사용 가치가 약하다.** 무료는 기본 할 일과 잠금화면 경험을 완결하고, 광고는 앱 내부의 보조 수익으로 운영한다. Pro는 개인화한 결과를 바로 적용하는 경험부터 개선하고, 이후 기존 할 일을 다시 입력하지 않게 하는 연동과 반복 작업 자동화로 강화하는 편이 적합하다.

가장 먼저 할 일은 광고 개수를 늘리는 것이 아니라 **실제 유료 매출과 테스트 데이터를 분리하고, 결제 전에 사용자가 원하는 결과를 완성하게 하는 것**이다. Paywall 기록 사용자는 33명, 구매 시작과 완료 기록 사용자는 각각 2명이다. 반면 광고는 현재 코드에서 테스트 전용이며 Release에서 꺼져 있다.

현재 저장소와 공개 배포 앱도 구분해야 한다. 저장소의 project.yml은 버전 1.1.4와 build 14이고, 확인한 공개 스토어는 1.1.7이다. 제공 데이터에는 이전 이름과 새 이름의 이벤트, 테스트 광고 이벤트가 함께 있다. 빌드별로 나누기 전에는 현재 코드 변경의 출시 효과로 해석할 수 없다. ## 3 총수익 0달러의 의미

**이 표의 0달러는 확인된 실제 매출이 없다는 표시이며, 실제 과금이 전혀 없었다는 결론은 아니다.**

현재 AnalyticsService는 purchase_completed를 구매 흐름을 확인하는 커스텀 이벤트로 보내고 is_revenue_event=0으로 구분한다. 체험은 value=0이고, 체험이 아닌 경우의 value도 조회한 상품 가격이다. 이 파라미터는 실제 청구 거래나 GA4 표준 매출과 동일하지 않다. 이벤트를 주요 이벤트로 지정하는 것만으로 실제 매출이 생성되지는 않는다. [현재 구매 이벤트 구현](/Users/nam/projects/ios/locktodonote/LockTodoNote/Core/Analytics/AnalyticsService.swift)

실제 매출은 다음 세 경로를 대조해야 한다.

1. App Store Connect에서 같은 기간의 판매·환불·구독 체험·유료 전환·수익금을 확인한다. 판매액과 개발자 수익금은 별도로 둔다.
2. 검증된 거래의 상품·거래 환경·최초 구매 또는 갱신·체험 여부를 연결한다. 현재 구매 CTA의 체험 자격만으로 실제 거래 종류를 확정하지 않는다.
3. Firebase 자동 구매 수집 여부를 확인한 뒤 수동 수익 이벤트 필요성을 판단한다. 자동 이벤트와 같은 거래의 수동 이벤트를 중복 매출로 합산하지 않는다. [Firebase 자동 수집 이벤트](https://support.google.com/analytics/answer/9234069?hl=en)

광고의 경우 현재 AdPolicy는 공식 테스트 광고 단위를 사용하고 Release에서는 false를 반환한다. Info.plist도 샘플 App ID다. 수익 콜백은 ad_test_revenue로 기록하며 ad_is_test=1이다. **이번 광고 53회는 운영 광고 실적이나 eCPM 추정의 근거로 사용하면 안 된다.** [광고 정책 코드](/Users/nam/projects/ios/locktodonote/LockTodoNote/Core/Ads/AdPolicy.swift), [Google 테스트 광고 안내](https://developers.google.com/admob/ios/test-ads)

실제 광고를 운영하려면 ID와 Release 분기뿐 아니라 테스트로 고정된 분석 필드 및 수익 기록 경로도 함께 바꿔야 한다. 운영 수익은 paidEventHandler의 금액·통화·정밀도를 사용하고 AdMob 보고서와 대조한다. SDK의 자동 광고 수익과 직접 전송한 값을 두 번 합산하지 않는다. [AdMob 노출별 수익 측정](https://developers.google.com/admob/ios/impression-level-ad-revenue)

## 4 무료 사용자에게 적합한 AdMob 운영안

### 배너를 먼저 운영할 위치와 조건

**첫 운영안은 캘린더 하단 적응형 배너 한 자리다.** 현재 AppShellView는 Today에서는 배너를 제외하고 캘린더와 설정 하단에 조건부로 표시한다. 10월 7일 문서의 Today 하단 설명을 현행 배치로 재사용하지 않는다. 설정 배너는 캘린더 운영을 본 뒤 비교할 후보로 두고, 처음부터 자리를 늘리지 않는다. [현재 배너 배치](/Users/nam/projects/ios/locktodonote/LockTodoNote/App/AppShellView.swift)

캘린더를 우선하는 이유는 기록 조회라는 자연스러운 체류가 있고 Today의 빠른 입력을 방해하지 않기 때문이다. 다만 top_destination_selected 363회는 모든 목적지가 합쳐진 수치다. 캘린더 체류와 무료 사용자 도달률이 충분하다는 증거는 아직 아니므로 destination별로 확인한다. settings_opened 41명도 유료 사용자와 테스트를 제외한 광고 도달 인원이 아니다.

운영 조건은 현재 구현의 보호 장치를 유지한다.

- 무료 권한 확인이 끝났고, 첫 활성화를 마친 뒤 다음 앱 사용 세션부터 노출한다.
- 화면이 전면이고 광고 영역이 실제 보일 때만 표시한다.
- 키보드·편집·사진 선택·Paywall·구매·복원·동의 양식·오류 복구 중에는 제외한다.
- 광고를 체크박스나 저장 버튼에 밀착시키지 않고 콘텐츠를 덮지 않는다.
- Pro 구매와 복원 직후 광고를 제거한다. StoreKit 무료 구독 체험으로 Pro 권한을 얻은 사용자도 포함한다.
- 광고 로딩이나 실패 때문에 콘텐츠를 기다리게 하지 않는다. 빈 광고 영역을 크게 남기지 않는다.

새로고침은 AdMob 설정과 SDK 동작을 사용하고 짧은 자체 타이머로 노출을 만들지 않는다. 고정 하단 배치에 맞는 적응형 크기와 iPhone·iPad 회전 시 공간은 실제 화면에서 확인한다. 현재 코드는 inline adaptive 크기를 사용하므로 고정 배너에 더 적합한 크기 방식은 출시 작업에서 판단한다. [AdMob 배너 가이드](https://developers.google.com/admob/ios/banner)

### 광고 형식별 우선순위

| 형식 | 권장 | 구체적 운영 |
| --- | --- | --- |
| 적응형 배너 | 1순위 | 캘린더 하단 한 자리로 시작 |
| 보상형 광고 | 2순위 실험 | 기존 무료 체험 뒤, 선택한 사진 또는 D-Day 템플릿 1개를 24시간 추가 사용 |
| 네이티브 광고 | 보류 | 현재 규모에서는 추가 UI와 운영 복잡도에 비해 검증 이득이 작음 |
| 일반 전면 광고 | 초기 제외 | 짧은 작성과 완료 행동을 끊을 가능성이 큼 |
| 앱 오픈 광고 | 초기 제외 | 빠르게 기록하려는 앱 진입 목적과 충돌 |

기존 24시간 템플릿 체험을 곧바로 광고 시청 뒤로 옮기지 않는다. 먼저 무료 체험이 실제 템플릿 사용과 유료 전환으로 이어지는지 확인한다. 보상 광고는 이후 별도의 선택지로 실험한다.

보상 CTA는 “광고를 보고 이 템플릿을 24시간 사용”처럼 내용과 기간을 명확히 표시한다. Pro 구매와 무료 템플릿 복귀도 함께 제공하고, 광고 없음이나 중도 종료 때 작성 내용은 보존한다. SDK 보상 획득 콜백에서 한 번만 지급하며 광고 클릭을 요구하지 않는다. 최초 실험은 설치 기준 전체 최대 3회로 제한하되, 이 숫자는 최적값이 아니라 구독 대체를 제한하기 위한 시작값이다. [Google 보상 광고 정책](https://support.google.com/admob/answer/7313578?hl=en)

선택한 템플릿만 여는 보상은 별도 만료 권한으로 구현해야 한다. 기존 temporaryTrialActive를 그대로 켜면 모든 Pro 템플릿이 열린다. 위젯 설치 체험과도 기간 중첩 정책을 맞추고 isPro=true로 대체하지 않는다.

### 광고가 가능한 영역과 운영 준비

Apple은 광고를 주 앱에 한정한다. 잠금화면 Live Activity·Dynamic Island·위젯·Share Extension에는 광고를 넣지 않는다. 단축어 요청과 수행 사이에도 광고를 삽입하지 않는다. 부적절한 광고 신고 경로를 제공한다. [Apple 심사 가이드 2.5.11 및 2.5.18](https://developer.apple.com/app-store/review/guidelines/)

운영 전에는 실제 AdMob App ID와 광고 단위, 앱 준비 상태, 적용되는 app-ads.txt 및 스토어 개발자 웹사이트 설정, 개인정보 공개를 맞춘다. 현재 UMP 흐름은 유지하고 canRequestAds 상태에서만 요청한다. 비개인화 옵션만으로 동의 처리가 끝났다고 보지 않는다. 추적을 도입할 경우 실제 데이터 처리에 맞춰 ATT와 공개 내용을 맞춘다. [UMP 가이드](https://developers.google.com/admob/ios/privacy)

일반 전면 광고를 앱 실행·종료 또는 매번의 버튼 조작 뒤에 넣지 않는다. 이는 제품 판단과 별개로 Google이 제한하는 배치도 포함한다. [금지되는 전면 광고 구현](https://support.google.com/admob/answer/6201362?hl=en)

## 5 현재 기능으로 유료를 확대할 수 있는 범위

### 첫 구매는 가능하지만 갱신 이유가 부족하다

사진과 D-Day, 원하는 템플릿을 사용하는 목적에는 첫 결제 이유가 있다. 그러나 한 번 꾸미고 나면 반복 결제 필요성이 작게 느껴질 수 있다. 무제한 단축어와 여러 구성은 반복 사용 가치가 있지만, 이번 자료에서는 각각 1명과 2명 수준의 이용 신호다. 현재 표만으로 이 기능들이 갱신을 견인한다고 판단할 수 없다.

광고 제거 역시 잠금화면만 주로 쓰는 사람에게는 노출 자체가 적어 강한 단독 판매 이유가 되기 어렵다. **주 혜택은 사용자가 얻는 결과이고 광고 제거는 보조 혜택**으로 두는 편이 적합하다.

구독 가치는 서버 기능에만 한정되지 않는다. 꾸준한 실질 업데이트와 반복해서 사용하는 도구도 가치가 될 수 있다. 다만 현재 기능으로 높은 가격의 구독을 지속할 수 있다고 보기에는 유료 사용과 갱신 자료가 부족하다. [Apple 구독 가이드 3.1.2](https://developer.apple.com/app-store/review/guidelines/)

### 지금 개선할 구매 흐름

추천 흐름은 **유료 템플릿 선택 → 내 내용으로 결과 완성 → 실제 적용 결과와 가격 확인 → 구매 → 사용 성공 확인**이다.

사진·D-Day 편집, 목적별 Paywall, 연간 기본 선택, 평생 상품 접기, 구매 후 결과 적용은 이미 구현돼 있다. 다시 만드는 대신 배포 여부와 실제 사용을 확인한다. 특히 사진 선택과 D-Day 조작이 눈에 띄고 이해하기 쉬운지 개선한다. ## 6 무료와 Pro의 권장 경계

| 영역 | 무료 유지 | Pro 강화 |
| --- | --- | --- |
| 핵심 기록 | 작성·완료·조회, 기본 반복, 기본 알림 | 기존 무료 기능을 다시 잠그지 않음 |
| 기본 표시 | Calendar Items, 기본 위젯과 Live Activity | 사진·D-Day·추가 템플릿과 테마 |
| 여러 구성 | 1개 저장 | 여러 개 저장·전환, 홈에서 쉽게 발견 |
| 빠른 입력 | 현재 단축어 하루 5회 | 무제한, 사용 위치별 안내 개선 |
| 반복 작업 | 기존 매일·평일·매주 | 요일 조합·격주·매 N일 등 새 고급 반복 |
| 기존 할 일 재사용 | 앱 내부 기록 | Apple 미리알림의 선택 목록을 지속 연동 |
| 다중 기기 | 로컬 사용 | 수요가 확인되면 iCloud 동기화 |
| 광고 | 제한된 앱 내부 배너 | 광고 제거 |
| 데이터 접근 | 작성한 데이터 보존과 기본 접근 | 만료를 이유로 기록을 잃게 하지 않음 |

신규 개발은 다음 순서가 적합하다.

1. **기존 Pro 기능의 발견과 적용 개선.** 여러 구성을 Today에서 발견할 수 있게 하고 “꾸민 설정 저장”임을 명확히 설명한다. 현재 이용 2명으로는 수요 부족과 발견 부족을 구분할 수 없다.
2. **고급 반복과 빠른 입력 개선.** 할 일 생성 43명과 완료 28명이라는 현재 사용에 가깝다. 기존 기본 반복을 유지하며 추가적인 시간 절약을 유료화한다.
3. **Apple 미리알림 연동 수요 확인 후 개발.** 다시 입력해야 하는 비용을 줄여 주는 후보지만 69명 자료에서 직접 요구가 확인된 것은 아니다. 앱 내 선택형 수요 조사로 검증하고 권한·완료·삭제·충돌 처리 범위를 정한다.
4. **iCloud 동기화는 다중 기기 수요가 확인된 뒤.** 설정의 Sync & Data라는 이름이나 App Group 공유를 클라우드 동기화로 판매하지 않는다.

자동 구성 전환은 Focus와 OS가 허용하는 범위를 확인한 뒤 검토한다. 현재 여러 구성 저장을 이미 자동화된 기능처럼 설명하지 않는다. 주간 통계와 AI 기능은 핵심 할 일 경험과 수익 병목을 먼저 해결한 뒤 검토한다.

[한국 가격](https://apps.apple.com/kr/app/locktodonote-%EC%9E%A0%EA%B8%88%ED%99%94%EB%A9%B4-%ED%95%A0%EC%9D%BC%EB%A9%94%EB%AA%A8/id6783183501), [미국 가격](https://apps.apple.com/us/app/locktodonote-lock-screen-todo/id6783183501)

한국의 평생 가격은 연간의 약 2.21배다. 장기 고객에게 평생이 유리한 구조지만, 실제 구독 잠식은 갱신율과 상품별 선택 자료로 확인해야 한다. 평생 판매를 줄이면 자동으로 총수익이 커진다고 볼 수도 없다.

### 단계별 권장안

| 단계 | 가격과 상품 운영 | 판단 기준 |

| 평생 가격 실험 | 29,000원 후보를 별도 검토 | 연간 대체와 추가 구매를 합친 60일·90일 수익 |

위 가격은 검증할 후보이며 최적 가격 추정치가 아니다. 한 번에 Paywall, 세 상품 가격, 광고를 모두 바꾸지 않는다. 공개 가격이 달라지면 같은 기간의 결과와 직접 비교할 때 유입 변화도 고려한다. 기존 상품 ID와 구매 권한은 유지하며 기존 구독자의 가격 보존 정책은 App Store Connect에서 결정한다.

동일한 고객 구성과 비용이라는 단순 조건에서는 연간 7,700원에서 9,900원으로 올릴 때 전환율이 기존의 77.8% 이상이면 최초 총 결제액은 유지된다. 실제 판단에는 체험 후 과금·환불·세금·유입 품질을 반영한다.

현재 기능이 주로 개인화에 머문다면 **평생 구매가 주력이 되는 경우도 수익 전략으로 수용할 필요가 있다.** 구독 비중 자체를 목표로 삼지 말고 고객당 수익과 유지 비용을 비교한다. 반복 기능이 사용되고 갱신이 확인될수록 연간 구독을 주력으로 강화한다. 기존 평생 구매자의 약속한 혜택을 축소하지 않는다.

## 8 수익 규모와 민감도 계산

### 광고 수익은 앱 안에서 발생한 실제 노출로 계산

아래는 사업 규모를 판단하기 위한 가정이며 시장 eCPM이나 현재 앱의 실적 추정이 아니다. 통화는 모두 원이고 환율은 사용하지 않았다.

가정은 광고 대상 무료 앱 DAU가 매일 일정하고, 대상 사용자당 하루 실제 배너 노출이 평균 1.5회이며, 한 달은 30일이다. 1.5회는 요청·충전·가시성 조건을 통과한 실제 노출이므로 충전율을 다시 곱하지 않는다. 잠금화면만 보는 사용자와 Pro는 DAU에서 제외한다.

월 광고 수익 = 광고 대상 무료 앱 DAU × 30 × 1.5 × eCPM ÷ 1,000

| 광고 대상 무료 앱 DAU | 월 실제 노출 | eCPM 500원 가정 | eCPM 1,500원 가정 | eCPM 4,000원 가정 |
| --- | ---: | ---: | ---: | ---: |
| 30명 | 1,350회 | 675원 | 2,025원 | 5,400원 |
| 100명 | 4,500회 | 2,250원 | 6,750원 | 18,000원 |
| 1,000명 | 45,000회 | 22,500원 | 67,500원 | 180,000원 |

현재 69명을 DAU로 넣어 예상 월매출을 계산하지 않는다. 운영 후 국가·형식·동의 상태·실제 노출별 eCPM을 대입한다. AdMob의 추정 수익과 지급액도 조정 및 지급 조건 때문에 같지 않을 수 있다.

중간 가정에서는 광고 대상 무료 앱 DAU 100명도 월 6,750원이다. 같은 가정으로 월 100만원을 광고만으로 만들려면 약 14,815명이 필요하다. 광고 노출을 위해 불필요한 앱 실행을 요구하는 것보다 유료 가치와 이용자 규모를 함께 키우는 방향이 적합하다.

### 연간 구독의 규모

아래는 연간 유료 권한을 유지하는 사용자가 100명이고 모두 같은 가격으로 결제했다고 가정한 연간 금액의 월 환산이다. 당월 신규 결제액이나 실제 입금액이 아니다.

| 연간 가격 가정 | 100명의 연간 총 결제액 | 월 환산 총 결제액 | 수수료 15%만 차감한 월 환산 |
| --- | ---: | ---: | ---: |
| 7,700원 | 770,000원 | 약 64,167원 | 약 54,542원 |
| 9,900원 | 990,000원 | 82,500원 | 70,125원 |
| 14,900원 | 1,490,000원 | 약 124,167원 | 약 105,542원 |

15%는 Small Business Program이 적용된다는 가정이다. 세금·환불·환율·운영비는 반영하지 않았으므로 실제 수익금은 다르다. 프로그램 적용 여부를 확인해야 한다. [Apple Small Business Program](https://developer.apple.com/app-store/small-business-program/)

같은 단순 가정에서 연간 7,700원 결제 1명의 수수료 차감액은 6,545원이다. eCPM 1,500원의 광고 약 4,363회와 같은 규모다. 짧게 앱을 사용하는 제품에서는 광고 몇 번의 추가 노출보다 한 명의 유료 전환을 얻는 가치가 클 수 있다.

보상 광고도 시청 수익만으로 평가하지 않는다. 추가 광고 수익과 보상 후 유료 증가분에서 유료 구매 대체분을 빼서 판단한다. 실제 지급받는 광고 수익에는 Apple 인앱결제 수수료를 다시 차감하지 않는다.

### 유입 확대 전에 확인할 단위 수익

예를 들어 신규 사용자 1,000명 중 실제 유료 연간 전환이 2%이고 모두 7,700원을 냈다면 최초 총 결제액은 154,000원, 15%만 차감하면 130,900원이다. 신규 사용자당 130.9원이며 세금과 환불은 제외했다. 이는 가정 예시로, 이번 2/69를 유료 전환율로 적용한 계산이 아니다.

따라서 유료 광고로 설치를 구매하기 전에는 국가와 유입별 60일·90일 수익을 확인한다. 초기에는 할 일 작성→잠금화면 표시→완료를 보여주는 스토어 소재와 유기적 유입을 우선한다. 다운로드 수보다 실제 핵심 행동과 유료 전환까지 연결되는 유입을 늘린다.

첫 1주에는 P0와 현재 기능의 배포 대응을 정리한다. 2주부터 4주에는 개인화 흐름과 한 자리 배너를 순차 적용한다. 5주부터 8주에는 결과에 따라 가격 또는 반복 기능 중 한 가지를 검증한다. 이는 권장 작업 순서이며 개발 일정의 확약은 아니다.

69명 단계에서 여러 A/B 실험을 동시에 돌리면 결제 몇 건에 결론이 크게 달라진다. 처음에는 한 번에 한 주요 변경을 적용하고 동일 조건의 코호트를 관측한다. 순차 비교에는 유입과 시기 차이가 섞일 수 있으므로 방향성 신호로 해석한다. 표본이 늘면 사용자별 고정 배정으로 대조군을 운영한다.

안정성 문제나 콘텐츠 저장·구매 권한 오류는 즉시 중단 조건으로 둔다. 수익 실험의 제품 경계로는 D7 유지율 3%포인트 이상 하락 또는 생성·완료 사용자 비율 10% 상대 감소 등을 시작값으로 정할 수 있다. 표본이 적을 때 한두 명의 차이를 확정 효과로 발표하지 않고, 충분히 성숙한 코호트와 실제 불편 사례를 함께 판단한다.

성공 기준은 광고 노출 수나 Paywall 수가 아니라 **동일 대상 사용자당 광고와 실제 결제 수익이 늘고 핵심 사용이 유지되는 것**이다. 구독 갱신 효과는 해당 갱신 시점이 지나야 판정할 수 있으며, 연간 상품의 60일·90일 결과만으로 연간 갱신 성공을 주장하지 않는다.
