# LockTodoNote 잠금화면 위젯과 광고 개선 보고서

2026년 10월 21일 기준. 기존 SwiftUI 구조와 무료 핵심 기능을 유지하면서 잠금화면 설치 안내, 표시·갱신, 위젯 구성 계측과 배너 광고 경로를 수정했다. 실제 기기에서 위젯을 설치하거나 운영 광고를 표시한 결과는 아직 없으므로 배포 검증 완료로 판정하지 않는다.

초기 Git 작업 트리는 깨끗했다. 9월 14일 분석, 10월 7일 광고 수정 기록, 10월 15일 수익·기기 검증 기록은 과거 자료로 참고했다. 과거 문서의 ‘Release 광고 비활성화’ 설명과 달리 작업 시작 시 현재 AdPolicy는 Release 운영 ID와 활성화 경로를 이미 가지고 있었다. 광고 ID를 새로 발급하거나 기존 Pro 상품·권한을 바꾸지 않았다.

## B 광고 개선 결과

기존 형식은 앱 내부 배너다. AppShellView가 Today·Calendar·Automation의 적격 상태와 무료 권한을 확인하고 위치별 배너를 소유한다. 전면·앱 오프닝·보상 광고를 추가하지 않았다. 위젯을 탭해도 광고 전용 화면으로 보내지 않는다.

UMP 정보 갱신 → 필요한 양식 → canRequestAds 확인 → SDK 초기화 → 활성 화면 배너 요청 순서다. 동의 갱신 실패 시 UMP가 이전 선택에 따라 요청을 허용할 때만 진행하며, 갱신 재시도는 60초 이내 차단한다. 동의 화면과 SDK 초기화를 중복 실행하지 않는다. 개인정보 선택을 열 때 기존 광고를 비활성화하고 세대 번호를 변경하여 이전 선택으로 로드한 객체가 재사용되지 않게 한다. 양식 종료 뒤에도 canRequestAds가 필요하다. publisher first-party ID 비활성화는 유지했다. [Google UMP 안내](https://developers.google.com/admob/ios/privacy)

앱은 ATT 권한을 직접 요청하거나 승인으로 간주하지 않는다. AdMob에 구성된 UMP ATT 메시지가 있다면 해당 흐름을 사용하며, IDFA 사용은 OS 권한에 따른다. ATT 미결정·거부·제한 상태를 승인으로 변경하는 코드는 없다. **AdMob 콘솔의 공개된 동의/ATT 메시지와 실제 기기의 허용·거부 결과는 별도 확인이 필요하다.** 개인정보처리방침 URL은 소스에 있으나 이번 웹 조회에서 본문에 접근하지 못해 정책 문구와 운영 설정의 최종 일치는 확인하지 못했다. [Google 개인정보 전략](https://developers.google.com/admob/ios/privacy/strategies)

SKAdNetwork는 2026년 10월 21일 [Google 공식 초기 설정 문서](https://developers.google.com/admob/ios/quick-start)의 식별자 50개를 중복 제거해 적용했다. 출처와 목록은 `skadnetwork-source-2026-10-21.json`에 보존했다. 이 설정은 설치 기여 측정을 위한 것이며 충전율·eCPM 상승을 보장하지 않는다.

배너는 성공·실패·노출·유료 콜백을 각각 기록한다. 백그라운드·화면 이탈·자격 해제 시 UIViewRepresentable을 해제하고 delegate와 paidEventHandler를 정리한다. 재시도는 백그라운드나 화면 밖에서 수행하지 않는다. 2회 재시도 후에는 화면 재진입으로 새 수명이 시작될 때 다시 시도할 수 있다. 운영 수익은 자동 수집될 수 있는 Firebase ad_impression과 custom ad_paid_revenue를 중복 합산하지 말고 AdMob 보고서와 대조한다.

현재 D1 약 1%, 광고 16회·$0.00이라는 과거 수치를 현재 실적으로 확인할 실시간 Firebase·AdMob 조회 권한/도구가 없다. 과거 집계에는 기간·빌드·테스트 트래픽 구분의 한계도 있다. 수익 0의 원인을 소스 수정만으로 확정하거나 개선 효과를 수치로 주장하지 않는다.

## C 위젯 사용성

앱과 확장은 `group.com.namslab.glancecard`를 공유한다. CardRepository가 JSON을 원자적으로 저장하고 CardStore의 성공 콜백이 DashboardCoordinator를 통해 공유 스냅샷 저장과 WidgetCenter 재로드를 요청한다. 추가·수정·삭제·완료·되돌리기는 기존 저장 경로를 유지한다. 확장 작업은 대기 큐에 보존하고 본앱 파일 저장 후 ID로 확인 처리한다. 공유 큐 잠금은 이 형식을 바꾸지 않는다. 파일 잠금을 열지 못하는 경우 프로세스 내 직렬화만 유지되므로, App Group 접근 및 다중 프로세스 동작은 기기에서 확인해야 한다.

| 흐름 | 개선 전 | 개선 후와 확인 범위 |
|---|---|---|
| 첫 할 일 작성 | 기존 4단계 선택형 온보딩과 홈 입력 | 단계 추가 없음, 저장 후 미리보기 유지. 10~20초 목표는 사용자 측정 전 가설 |
| 설치 안내 접근 | 설정 안의 표시 화면, 홈 화면 위주 설명 | 온보딩 활성화 단계의 선택형 버튼과 홈 입력 아래 안내 버튼 |
| 안내 기본 화면 | Live Activity 탭 우선 | 위젯 탭 우선, 잠금 해제 → 잠금화면 길게 누르기 → 사용자화 → 위젯 추가 |
| 설치 완료 후 | 종류 구분 없는 설치 확인 | accessoryRectangular·accessoryInline 구성 확인 후 반복 설치 단계와 홈 안내 진입 버튼 숨김 |
| 0개·모두 완료 | 액세서리 첫 항목 또는 빈 줄 | 남은 항목이 없다는 문구, 완료 항목이 먼저 가리지 않음 |
| 여러 개·긴 글 | 날짜 열이 제한된 공간을 점유 | 직사각형에서 첫 미완료 최대 두 줄과 다음 항목 한 줄, inline은 첫 미완료 한 줄 |
| 언어·이모지 | SwiftUI Text와 기존 현지화 | 같은 Text 경로 유지, 강제 문자 단위 절단 없음. 넘치는 글은 공간상 말줄임되므로 전체 표시를 보장하지 않음 |
| 앱 종료 후 날짜 변경 | 캐시의 준비된 날짜에 의존 | iOS 16.2 이상에서 저장된 카드·대기 입력·반복·이월을 재구성; 16.1은 기존 캐시 경로 |
| 명시 날짜 선택 | 현재 날짜용 calendarDays가 덮어쓸 수 있음 | 명시 날짜의 스냅샷을 유지 |
| 개인정보 | 앱의 hidden/countOnly/titleOnly 설정 | 설정과 기본 공개 범위를 유지하고 WidgetKit privacySensitive 추가; 개수 모드 0 오류 수정 |

WidgetKit의 갱신 예산·일정은 OS가 결정한다. 추가·수정 시 재로드 요청은 보내지만 즉시 반영은 보장하지 않는다. 부팅 후 최초 잠금 해제 전에는 보호된 원본 파일을 읽지 못할 수 있어 기존 공유 스냅샷으로 폴백한다. 신규 설치·기기 재부팅·업데이트·여러 위젯·잠금 중 가림은 실기기 검증 대상이다. 직사각형 미리보기는 현재 데이터와 개인정보 모드를 반영하는 앱 내 모형이며 시스템의 정확한 렌더링 결과 캡처가 아니다.

## D Firebase 계측

| 이벤트 | 정의와 중복 처리 |
|---|---|
| first_todo_created | 기존 최초 생성 플래그와 이벤트 유지, 최초 성공 저장 시 한 번 |
| todo_created | 기존 성공 생성 이벤트 유지, 사용자 입력 본문 미전송 |
| todo_completed | 기존 본앱·확장 완료 이벤트 유지, 확장 원래 시각과 event_id 보존 |
| widget_setup_guide_viewed | 안내 화면이 표시될 때. 기존 widget_setup_started를 대체하며 둘을 동시에 보내지 않음 |
| widget_configured_detected | 성공 조회에서 하나 이상 구성됐고 종류별 수가 직전 관측과 다를 때 |
| widget_opened | source=widget 딥링크로 앱이 열릴 때. 기존 widget_open_app를 대체하며 이중 발행하지 않음 |
| widget_configuration_check_failed | OS 구성 조회 오류. 오류 코드를 보내며 ‘미설치’로 기록하지 않음 |
| widget_configuration_checked | 성공 조회마다 종류별 수와 변경 여부, 설치 해제도 0으로 기록 |
| widget_installed_confirmed | 기존 이벤트 유지. 신규 확인은 실제 잠금화면 계열 구성에서만 활성화 신호로 인정 |

새 이벤트의 home_count·rectangular_count·inline_count·widget_count는 구성 수다. 공통 widget_configuration_state는 마지막 성공 관측 기준 unknown·none·home_only·lock_screen이다. 실패하면 관측값은 보존하고 화면은 확인 불가로 표시한다. family는 지원 형식을 구분하며 실제 잠금화면 노출 위치나 읽기 행동까지 증명하지 않는다. [Apple 현재 구성 조회 API](https://developer.apple.com/documentation/widgetkit/widgetcenter/getcurrentconfigurations(_:))

GA4 또는 BigQuery에서 배포 빌드와 실제 조회 기간을 고정하고 다음을 비교한다.

1. first_open 코호트 중 first_todo_created 도달률과 안내 도달률.
2. 성공 조회 사용자 중 lock_screen·home_only·none 비율. unknown과 실패는 미설치 분모에서 제외.
3. 구성 확인일 이후 7일의 todo_created·todo_completed와 기존 수정 이벤트/계약을 사용한 직접 관리 행동. 수정 이벤트가 없는 경로는 생성·완료와 동일한 지표로 가정하지 않는다.
4. widget_opened 사용자 비율과 전체 앱 실행을 별도 지표로 표시.
5. 코호트 최초 관측 상태를 고정해 구성 사용자와 미구성 사용자의 D1·D7·D30을 비교. 나중에 설치한 사람을 처음부터 설치군으로 분류하지 않음.

기존 이름은 과거 빌드에만 남으므로 기간을 연결할 때 widget_open_app와 widget_opened, widget_setup_started와 widget_setup_guide_viewed를 빌드별로 정규화한다. 기존 활성화 플래그에는 홈 위젯 확인이 섞였을 수 있어 새 구성 조회 이벤트로 잠금화면 코호트를 정한다. 메모·할 일 본문과 개인 이름은 신규 이벤트에 포함하지 않는다.

OS는 실제 위젯 노출·읽은 횟수를 제공하지 않는다. 앱이 실행되지 않은 동안 설치·해제를 실시간으로 알 수 없고 구성 수가 그대로인 삭제·재설치도 구분할 수 없다. widget_timeline_requested는 렌더링 요청 지표다. 확장 큐 이벤트는 앱 복귀 전까지 Firebase로 전달되지 않을 수 있으며 occurred_at_ms가 GA4의 기본 수신 날짜를 자동 변경하지 않는다.

## E 리텐션과 수익 모델 평가

1. **설치 장애물:** 홈 화면과 잠금화면의 다른 설치 절차가 설명되지 않았고 설정 안에 숨겨져 있었다. 현재는 첫 콘텐츠를 만든 단계와 홈에서 바로 안내에 접근할 수 있다. iOS 자동 설치 기능은 구현하지 않았다.
2. **설치 후 앱을 다시 쓰는 이유:** 작성·수정·삭제·완료 취소와 날짜별 계획 관리다. 앱 재방문을 위젯 읽기의 전제 조건으로 삼지 않는다.
3. **위젯만 쓰는 사용자:** 필요한 할 일을 정확하게 읽는다면 제품 가치가 성립한다. 앱 D1이 낮아도 단독으로 실패로 판단할 수 없으며 직접 읽기 여부는 측정할 수 없다.
4. **현재 가장 불편한 부분:** Live Activity와 지속 설치되는 위젯을 구분해 이해해야 하고, 작은 위젯에서는 긴 문장을 모두 읽을 수 없다. 개선 후에도 실제 기기에서 크기·문구·설치 시간을 확인해야 한다.
5. **가장 작은 다음 개선:** 첫 저장 → 안내 진입 → 잠금화면 계열 구성 확인의 이탈 구간을 관측한다. 10~20초 첫 입력과 설치 성공 여부를 소수 신규 사용자 테스트로 재고, 실제 막히는 문구만 고친다.

위젯 구성 사용자 수·앱 실행 빈도·광고 기회·자리별 수익·사용자당 수익의 현재 운영 수치는 미확인이다. 배너는 무료 적격 사용자가 앱 화면을 볼 때만 기회가 생긴다. 위젯만 보는 사용자는 광고 노출 기회로 계산하지 않는다. 기존 Pro에는 광고 제거 외 표시·자동화 기능과 StoreKit 구매 권리가 이미 있으므로 신규 Pro나 가격 변경을 추가하지 않았다. 짧은 앱 세션에서는 광고 제거만의 가치가 작을 수 있다. 실제 수익과 재방문 자료를 확보한 후 기존 Pro 가치와 운영 배너를 평가하는 편이 타당하다.

## G 배포 준비

서명 없는 iOS 기기용 Release 빌드와 Widget Extension 컴파일·패키징이 성공했다. 실제 산출물 Info.plist에서 버전 1.1.8, Bundle ID com.namslab.glancecard, SKAdNetwork 50개가 출처 목록과 정확히 일치함을 확인했다. 앱과 확장의 처리된 plist, 빌드 로그, verification.json을 QA 폴더에 저장했다. 이 빌드는 컴파일과 패키징만 확인하며 App Store 업로드·TestFlight 배포를 확인하는 절차는 아니다. 기존 사용자 메모와 App Group 키, 상품 ID, 기본 개인정보 설정은 보존했다. WidgetKind도 유지하여 기존 위젯 등록을 교체하지 않는다.

TestFlight 준비 완료로 판정하려면 실패한 기존 테스트 계약 정리, 서명 Archive와 기존 설치 업데이트, 무료/Pro 광고 차단, 운영 콘솔 동의 양식·개인정보 정책 및 실제 기기 위젯 시나리오를 확인해야 한다.


## H 연결된 iPad 후속 검증

10월 21일 iPad Air 11인치 M2, iPadOS 26.6.2에서 이벤트 계약 17개와 기존 데이터 초기화 없는 핵심 UI 테스트 1개가 통과했다. 할 일 생성·수정·재실행 유지·삭제·완료, 설치 안내 화면, Google 공식 테스트 배너 실제 노출과 Pro QA 광고 차단을 확인했다. 앞서 디스크 부족으로 막혔던 앱 이벤트 계약 검증은 이 실기기 실행으로 해소됐다.

원본 카드 5개의 내용·완료 상태와 ID, 저장한 구성은 보존됐다. 기존 미완료 이월에 의해 날짜와 updatedAt은 갱신됐다. 최종 OS 구성 관측은 홈 화면 위젯 1개, 잠금화면 계열 0개다. 잠금화면 실제 표시·갱신·탭 검증용 빌드는 Mac 디스크 부족으로 중단되어 완료로 판정하지 않는다. UMP·ATT 전체 상태와 No Fill, 재부팅·업데이트·잠금 중 가림도 남아 있다.

세부 결과와 증거 위치는 [iPad 실기기 테스트 결과](ipad-retention-test-report-2026-10-21.md)에 정리했다. 전체 공유 테스트의 기존 assertion 3건 실패와 이번 선택된 실기기 테스트 통과는 구분한다.
